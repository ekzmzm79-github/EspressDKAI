# 검토 요청: 구현 계획서

- 요청일: 2026-10-28 · 단계: M0 시작 전 · 상태: 요청
- 대상: [`docs/implementation-plan.md`](../implementation-plan.md)

## 배경

EspressDKAI는 매일 아침 LLM 개발사 소식과 국내 AI 채용·해커톤 소식을 수집해 한 장짜리 카드뉴스 웹으로 공개하는 1인 프로젝트다. Claude Code 클라우드 예약 작업이 수집하고 데이터 JSON을 PR로 올리면, 사람은 휴대폰에서 Merge만 누르고, 검사·생성·배포는 GitHub Actions가 한다. API 키 없이 Claude 구독 사용량 안에서 돈다. 공개 페이지는 운영자 이름으로 나간다.

## 검토 대상

계획서 전체. 특히 0장(기획서 대비 변경), 4장(이어 쓰기 PR), 6장(Actions와 권한). 기획서의 수집 주제·섹션 선정은 범위 밖이다.

## 질문

1. **이어 쓰기 PR(4장):** 열린 PR 하나에 매일 커밋을 추가하는 방식에서, 사람이 PR 중간에 `/drop`을 한 뒤 다음 날 실행이 같은 브랜치에 이어 쓸 때 충돌이나 데이터 유실이 생길 경로가 있는가?
2. **추가 전용 데이터(2·3장):** 색인을 파일로 두지 않고 `days/`·`runs/`·`decisions/`에서 매번 파생할 때, 7일 범위 판단이나 "스킵 후 재후보" 규칙에서 빠진 경우가 있는가?
3. **두 섹션이 비는 날(4장):** 열린 PR이 없을 때 별도 로그 PR을 자동 Merge하는 흐름이 이어 쓰기 PR과 동시에 존재할 때 경쟁 상태가 생기는가?
4. **권한(6장):** `issue_comment` 기반 `/drop`, GitHub App 토큰, main 보호 우회 구성에서 공개 저장소 기준으로 악용 가능한 경로가 있는가?
5. **검사 규칙(5장):** 배포를 막는 항목과 경고만 하는 항목의 구분이 적절한가? 막아야 하는데 빠진 것이 있는가?
6. **전반:** 1인 운영 규모에 비해 과한 부분, 덜어낼 수 있는 부분이 있는가?

## 이미 고려한 것

- **매일 새 PR:** Merge가 밀리면 다음 실행이 어제 데이터를 못 보고 중복을 만들고, 공유 색인 파일에서 충돌이 나서 버렸다.
- **주 단위 실행:** 승인 부담은 줄지만 "매일 흐름 파악"이라는 1차 목적과 맞지 않고, 한 세션 수집량이 커져 검증 품질이 떨어져서 버렸다.
- **링크 실패 시 배포 중단:** Actions IP를 막는 사이트가 많아 정상인 날도 멈춰서 경고로 낮췄다.
- **Claude가 정오 Merge까지 수행:** 구독 사용량을 쓰고 이유가 없어, GitHub Actions 예약 워크플로로 했다.
