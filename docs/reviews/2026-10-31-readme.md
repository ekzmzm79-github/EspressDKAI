## 배경

EspressDKAI는 매일 아침 AI가 AI 채용·해커톤 소식과 주요 AI 기업 소식을 모아 검증하고, 사람이 승인하면 한 장짜리 웹페이지로 공개하는 1인 프로젝트다. 기획부터 운영까지 여러 AI 세션과 모델(Claude, Gemini, ChatGPT)에 역할을 나눠 맡겼다.
이 README는 저장소의 첫 화면이면서 **포트폴리오의 프로젝트 지면**이다. 내용은 운영자 인터뷰로 정리한 소개와 에피소드에서 가져왔다.

위쪽은 포트폴리오 독자용, 구분선 아래는 개발자용으로 나눴다.

## 검토 대상

README 본문의 구성, 분량, 첫 화면 인상, 문장. 사이트 디자인과 코드는 범위 밖이다.

## 질문

1. **첫 30초:** 제목부터 첫 스크린샷까지만 보고 이 프로젝트가 무엇이고 왜 볼 만한지 전달되는가? 첫 이미지로 PC 화면이 맞는가, 휴대폰 화면이 맞는가? (주 사용 장면은 휴대폰)
2. **AI 협업의 드러남:** "AI와 함께 만든 방식"과 "판단의 순간들"이 "AI를 썼다"가 아니라 "AI에게 일을 나누고 판단은 사람이 했다"로 읽히는가? 어느 문장이 그걸 흐리는가?
3. **분량:** 판단의 순간들 3개가 각 3~5문장이다. 줄여야 한다면 어느 것을 어떻게 줄이고, 원문 에피소드로 링크를 걸 만한가?
4. **순서:** 왜 → 무엇 → 어떻게 → AI 협업 → 화면 변화 → 현재 상태. "AI와 함께 만든 방식"을 더 위로 올려야 하는가?
5. **이미지:** 이미지 6장(첫 화면, 휴대폰 2장, 흐름도, 개편 전후)이 많거나 겹치는가? 빼거나 합칠 것이 있는가?
6. **빠진 것:** 면접관이 이 README를 보고 가장 먼저 물을 질문인데 README에 답이 없는 것이 있는가?

## 이미 고려한 것

- **회고는 넣지 않는다.** 시작 사흘째라 운영이 안정된 뒤에 쓴다.
- **에피소드 원문은 이 저장소에 없다.** 별도 비공개 저장소에서 관리한다. README에는 요약과 근거 PR 링크만 둔다.
- **영어판은 지금 만들지 않는다.** 주 독자가 국내 채용이다.
- **검토는 이번 한 번만 받는다.** 이 프로젝트의 원칙이다(README "교차 검토를 한 번에서 끊다").

#### 1. 첫 30초 인상과 첫 이미지 (Q1)

- **첫 문장의 엔지니어링 밀도 보강 필요:**
  - 현재 첫 줄(`AI 채용·해커톤 소식과 주요 AI 기업 소식을 매일 아침 한 장으로. AI가 모으고 검증하고, 사람이 승인한 것만 공개하는 브리핑 사이트.`)은 서비스 기능만 설명해, 얼핏 보면 단순 크롤링·요약 토이 프로젝트처럼 읽힐 수 있다.
  - **개선 제안:** 바로 아래 한 줄로 **기술적·구조적 특징**을 짚어 주는 것이 좋다.
    > 예시: *"별도 DB나 어드민 서버 없이, 다중 AI 에이전트(수집·독립 검증)와 GitHub PR·Actions만으로 구축한 Human-in-the-Loop 브리핑 파이프라인."*
- **첫 이미지 선택과 촬영 기준일 문제:**
  - 현재 첫 이미지(`site-desktop.png`)는 히어로 영역이 96vh로 넓어지면서 **정작 브리핑 카드가 어떻게 생겼는지 전혀 보이지 않고**, 아래 64행(화면이 바뀐 과정)에 **완전히 똑같은 이미지 파일이 두 번 중복 삽입**되어 있다.
  - 또한 `site-desktop.png`, `site-mobile-hero.jpg`, `site-mobile-cards.jpg` 모두 10/30 데이터를 10/31 기준으로 렌더링해 찍어서 배지가 **`1일 전 헤드라인`**으로 나오고, `site-mobile-cards.jpg`의 카드 머리 블록이 오늘 소식의 크레마 골드색이 아니라 **어두운 지난 소식 색상**으로 죽어 있다.
  - **개선 제안:**
    1. 스크린샷은 모두 **`?today=2026-10-30`(데이터 당일 기준)**을 붙여 다시 찍어 `TODAY'S HEADLINE`과 크레마 골드 카드가 살아나게 한다.
    2. 첫 자리에는 주 사용 장면인 **휴대폰 첫 화면(`site-mobile-hero.jpg`)과 카드 화면(`site-mobile-cards.jpg`) 2열 배치**(또는 PC 히어로 + 스크롤된 카드 섹션이 함께 보이는 이미지)를 바로 보여 주고, 현재 28~31행에 따로 떨어져 있는 모바일 이미지 블록과 합치는 편이 첫 30초에 "히어로 임팩트 + 실제 카드뉴스 UI"를 한 번에 보여 줄 수 있다.

#### 2. "AI를 썼다" vs "사람이 설계·판단했다"의 드러남 (Q2)

- **인상을 흐리는 문장 2곳:**
  - 48행: `"3. 디자인: Claude가 데모를 만들고, Gemini가 방향 지시대로 개편하고, 다시 Claude가 검수했다."`
  - 55행: `"다른 모델의 디자인 개편을 검수하다. Gemini의 개편을 Claude가 휴대폰·PC 화면, 키보드 조작, 접근성 검사, '9일 뒤에 연 화면'까지 확인해 8건을 고쳤다."`
  - **문제점:** 문장의 주어가 모두 AI 모델(`Claude가 ~하고, Gemini가 ~하고`)로 되어 있어, 빠르게 읽는 면접관에게 **"지원자(사람)는 중간에서 프롬프트와 결과물만 옮긴 전달자였나?"**라는 오해를 줄 수 있다.
- **개선 제안 (주어를 '사람의 설계·디렉팅'으로 전환):**
  - **48행 수정 방향:** *"3. 디자인과 검수 분리: 시각·인터랙션 연출은 Gemini에게 구체적인 UX 방향(첫 화면 시선 집중, 지표 하단 분리, 3D 스크롤 스케일업)을 지시해 개편하고, 정적 분석과 엣지 케이스 검증에 강한 Claude에게는 Playwright·axe 기반 접근성 및 상태 검수를 맡겨 역할 충돌을 막았다."*
  - **55행 제목·첫 문장 수정 방향:** 제목을 `"다른 모델의 디자인 개편을 검수하다"` 대신 **`"생성한 모델과 검수하는 모델을 분리해 빈틈을 잡다"`**로 바꾸고, *"한 모델이 화려한 인터랙션을 만드는 데 집중하면 접근성이나 예외 상태('9일 뒤에 연 화면' 등)를 놓치기 쉽다. 그래서 개편 직후 다른 모델 세션에 실제 브라우저 렌더링·키보드 조작·기계적 접근성 검사를 지시해 8건을 잡아냈다."*처럼 **왜 사람이 교차 검수 파이프라인을 설계했는지**가 주어가 되게 쓴다.

#### 3. '판단의 순간들' 분량과 호흡 (Q3)

- 에피소드 3개 선정은 모두 훌륭하나, 현재 각 항목이 줄글 4~5문장으로 이어져 있어 훑어읽기에는 호흡이 길다.
- 원문 에피소드는 비공개 저장소에 있으므로 외부 링크는 걸지 않는 것이 맞다(깨진 링크나 권한 오류는 포트폴리오에서 감점 요인).
- **개선 제안:** 각 항목을 3문장 이내(`문제 발견 → 기각한 대안과 이유 → 채택한 해법과 검증 PR`)로 조이되, 핵심 구절만 굵게 표시하거나 줄바꿈을 주면 분량을 크게 덜어내지 않고도 30초 스캔이 가능해진다.
  - 특히 첫 번째 항목(`승인을 깜빡해도 꼬이지 않는 PR 흐름`)에서 *"주기를 일주일로 늘리는 안은 버렸다. 매일 흐름을 보는 게 목적이고, 마감이 주중에 지나가기 때문이다."*는 도메인 목적에 기반한 좋은 판단이므로 살리되, 문장을 *"주간 브리핑으로 바꾸면 마감 임박 채용을 놓치므로 일간 주기는 유지하고, 대신 열린 PR 하나에 커밋을 이어 쌓는 구조로 풀었다 ([#8](...))."*처럼 한 문장으로 압축할 수 있다.

#### 4. 섹션 순서 (Q4)

- 현재 `왜 만들었나`와 `무엇을 하나`가 별도 `##` 섹션으로 나뉘어 있어, 핵심인 `어떻게 돌아가나`와 `AI와 함께 만든 방식`이 나오기까지 스크롤이 길다.
- **추천 순서:**
  1. **도입부 (제목 + 한 줄 정의 + 라이브 링크 + 대표 스크린샷)**
  2. **`## 왜, 무엇을 만들었나`** (`왜 만들었나` 2문단 + `무엇을 하나`의 표와 핵심 규칙 3줄을 한 섹션으로 통합)
  3. **`## 어떻게 돌아가나`** (`flow.png` + 운영·검증 원칙)
  4. **`## AI와 함께 만든 방식` & `### 판단의 순간들`** (면접관이 가장 관심 있게 볼 엔지니어링 판단을 앞당김)
  5. **`## 화면이 바뀐 과정` & `## 현재 상태`**
  6. **`## 개발자용`**

#### 5. 이미지 6장 구성 점검 (Q5)

- **중복 및 비율 불균형 해결 필요:**
  1. **중복 제거:** `site-desktop.png`가 8행과 64행에 중복 사용되고 있다.
  2. **62~65행 개편 전후 비교(`demo-desktop.png` vs `site-desktop.png`)의 세로 비율 불일치:**
     - 왼쪽 `demo-desktop.png`는 전체 페이지 세로 풀샷(`1280×1546`)인데, 오른쪽 `site-desktop.png`는 첫 화면 히어로만 찍은 가로샷(`1280×800`)이다. `width="49%"`로 나란히 놓으면 왼쪽은 길고 오른쪽은 짧아 시각적 균형이 깨진다.
     - **해결:** 오른쪽 개편 후 이미지도 카드 섹션과 하단 파이프라인 지표까지 포함된 전체 화면(또는 같은 종횡비로 크롭한 이미지)을 쓰거나, 위쪽 도입부에 PC 대표 화면을 두고 개편 전후 비교는 모바일 전후(`real-mobile.png` vs 개편 후 모바일) 또는 같은 높이로 맞춘 데스크톱 비교 이미지로 통일하는 것이 깔끔하다.

#### 6. 면접관이 가장 먼저 물을 질문인데 빠진 것 2가지 (Q6)

1. **"왜 별도 DB나 어드민 웹페이지 없이 GitHub PR과 정적 JSON 파일로 설계했나요?"**
   - 이 프로젝트에서 가장 영리한 아키텍처 결정인데 README 본문에는 "어떻게 동작하는지"만 있고 **"왜 이 구조를 택했는지(Why GitHub as Backend & Admin)"**가 명시되어 있지 않다.
   - `어떻게 돌아가나` 절에 다음 두 가지를 한 줄씩 명시하면 기술 면접 방어력이 크게 올라간다:
     - **서버·유지비 0원의 모바일 백오피스:** GitHub 모바일 앱 자체가 푸시 알림, Diff 확인, `/drop <id>` 코멘트를 통한 항목 부분 제외, PR 닫기를 통한 거절 기록까지 수행하는 어드민 인터페이스가 된다.
     - **추가 전용(Append-only) 데이터로 충돌 원천 차단:** AI는 그날의 `data/days/YYYY-MM-DD.json` 파일만 새로 만들고, 최근 7일 색인은 스크립트가 매번 파생(`scripts/index.py`)시키므로 여러 실행이나 PR 사이에서 공유 색인 파일 충돌이 원리적으로 발생하지 않는다.
2. **"AI가 요약하면서 사실을 지어내거나(환각) 형식을 어기는 건 어떻게 막나요?"**
   - 현재 40행에 *"별도 에이전트가 원문과 대조한다"*고만 적혀 있는데, **① 독립 에이전트의 의미적 원문 대조(초안 작성 컨텍스트 분리) + ② `validate.py`를 통한 기계적 차단(JSON 스키마, 인용 40자 제한, 마감일·날짜 정합성, 7일 내 동일 URL 자동 제외) + ③ 사람의 최종 승인**이라는 **3중 검증 구조**로 묶어 표현하면 훨씬 체계적으로 읽힌다.
